# ai-powered-dev-sandbox

生成 AI を使った開発を色々と試すためのリポジトリ。

## 利用する生成 AI ツール

### 基本となる AI ツール (コーディングエージェントなど)

* Visual Studio Code 上で動く AI エージェント
  * GitHub Copilot
  * Codex
* Codex アプリ

### MCP サーバー

* [GitHub MCP サーバー](https://github.com/github/github-mcp-server)

## 開発の進め方

以下のような形で開発を進める。

* 変更要求: GitHub の issue で作成
* 要件整理: issue を基に生成 AI と対話しながら仕様を詰めていく。 不明点は随時 issue 上でやり取り
* 製品仕様・アーキテクチャ策定: 要件整理の中で製品仕様やアーキテクチャ設計も策定していく
  * ドキュメントは docs/spec、docs/architecture ディレクトリに保存する
  * 製品仕様としては、外部との入出力及び副作用と、概念的なデータモデルに特に注力する
* 実装・テスト: テスト駆動開発の形で、製品仕様・アーキテクチャ設計を基にテスト記述と実装を進める
  * E2E テストは tests ディレクトリに保存する
  * ソフトウェア製品のソースコードは product/{component_name} ディレクトリに保存する

### 具体的な作業手順

#### 変更要求

* 作業主体者: 変更要求者 (製品に変更を加えたい人)
* 目的: 変更したい意図を明文化する
* 具体的な作業内容
  * GitHub リポジトリに新たな issue を作成し、変更要求の内容を記述する

#### 要件定義・仕様策定・基本設計

* 作業主体者: 製品開発者 (ソフトウェアエンジニア、デザイナー)
* 関係者: 変更要求者 (製品に変更を加えたい人、issue を作成した人)、QA 担当者
* 目的: 変更内容を明確にし、内容について関係者間で合意する
* 具体的な作業内容
  * 製品開発者は issue に対応する新しいブランチを作成し、作成できるタイミングで pull request を作成する
  * Issue 内容確認: 以下の内容を必要に応じて繰り返す
    * 製品開発者及び QA 担当者は、issue の内容を確認し、不明点があれば issue のコメントで変更要求者に質問する
    * 変更要求者はコメントで返信したり issue 内容を更新して質問に答える
  * 仕様策定・アーキテクチャ設計: 以下の内容を必要に応じて繰り返す
    * 製品開発者は、新しいブランチ上で docs/spec や docs/architecture ディレクトリ内に製品仕様やアーキテクチャ設計を記述する (あるいは既存のドキュメントを更新する)
    * 更新された内容は GitHub 上に push する (pull request が更新される)
    * 変更要求者及び QA 担当者は、pull request 上で更新内容を確認し、レビューする
* 備考
  * もしこの段階でデプロイタイミングを分けたい内容であることが明確な場合は、ブランチ及び pull request を分けておくこと (※ issue も分けるかは要議論)

#### 実装・テスト

* 作業主体者: 製品開発者 (ソフトウェアエンジニア、デザイナー)
* 関係者: 変更要求者 (製品に変更を加えたい人、issue を作成した人)、QA 担当者
* 目的: 要件定義・仕様策定・基本設計にて記述された変更を実現する
* 具体的な作業内容
  * 製品開発者は要件定義・仕様策定・基本設計の際に作成された仕様やアーキテクチャを確認し、実装計画を立てる
    * 複数に分けて実装してもよいし、単発で実装してもよい
    * 実装計画は要件定義・仕様策定・基本設計の際に作成された pull request の description 内にタスクリストの形で記載する
  * 製品開発者は、上記の実装計画に沿って次の形で実装を繰り返す
    * 複数に分ける場合は、要件定義・仕様策定・基本設計の際に作成されたブランチから新しいブランチを作成して作業を開始する (pull request 作成できるタイミングで pull request は作成しておく。 マージ先は要件定義・仕様策定・基本設計の際に作成したブランチとする。 作成した pull request は、要件定義・仕様策定・基本設計の際に作成した pull request から辿れるようにリンクを追加する)
      * 単発で実装する場合は、そのブランチ上で作業して良い
    * テスト駆動開発の形で、E2E テストからユニットテストまでのテストも記述しながら製品の実装を進める
    * 実装が終わりテストが通ることも確認出来たら、レビューを依頼する (レビュアはソフトウェアエンジニアや QA 担当者)
    * レビューに通ったらマージする
* 備考
  * 作業中に製品仕様やアーキテクチャ設計に関して更新が必要になった場合は、随時更新を行う

#### 変更の取り込み

* 作業主体者: 製品開発者 (ソフトウェアエンジニア、デザイナー)
* 関係者: 変更要求者 (製品に変更を加えたい人、issue を作成した人)、QA 担当者
* 目的: 実現された変更内容をデプロイ可能にする
* 具体的な作業内容
  * 製品開発者は、要件定義・仕様策定・基本設計の際に作成された pull request に全ての実装がマージされていることを確認する
  * 製品開発者は、要件定義・仕様策定・基本設計の際に作成された製品仕様・アーキテクチャ設計を満たしていることを確認する
  * 変更要求者及び QA 担当者は、改めて製品仕様と実際に動く製品を確認し、デプロイ可否判断を行う
  * デプロイ可と判断されたならば、マージする
  * 不可と判断された場合は、修正すべき箇所に戻って修正を行う
